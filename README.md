# Project: GameShelf

A browsable catalog of 42 video games that you can search, filter and sort.

This is a capstone for everything in the Odin Project Foundations course. The three
Foundations projects each drill one thing: Rock Paper Scissors is logic, Etch-a-Sketch is
creating elements, Calculator is state. GameShelf is the first one where you have to do
all three at once, against real data, and make it look good.

When you are done you will have something worth putting in front of people — which is
more than most "learning projects" can say.

## Getting started

**1. Make your own copy.** Green **Use this template** button → **Create a new repository**.
Name it whatever you want.

**2. Set the visibility to Public.** This matters. GitHub only serves a live website from a
*public* repository on a free account, and step 3 below puts this online — so choosing
Private would quietly cost you that, and you would not find out until you got there. Nothing
in here is secret, and the whole point is to end up with something you can show people.

**3. Clone *your* repo and open it.**

```bash
git clone <the URL of YOUR new repo, not the one you copied from>
cd <your-repo-name>
```

Then open `index.html` in your browser. There is nothing to install and nothing to build —
it is a few files and a browser, which is exactly how the web started.

## What you are starting with

```
index.html          boilerplate, an empty <main>, and the script tags in the right order
styles.css          empty, apart from a five-line reset
app.js              empty, apart from one console.log to prove the data loaded

data/games.js       DONE. 42 games. Do not edit this file.

design/DESIGN.md    DONE. The design, specified exactly. Read this before you write CSS.
design/tokens.css   DONE. Every colour, size and spacing value, as CSS variables.
design/mockup-*.png What the finished thing looks like — wide, narrow, and empty.

.github/             an issue template that gives you a progress checklist. See step 3.
```

Two things are already decided for you, on purpose: **the data** and **the design**. You are
here to learn to build, not to type in release years or pick hex codes. Everything in
`data/` and `design/` is a given — the same way a real ticket arrives with the content
written and the design signed off.

Open `index.html` in your browser right now, open the console with F12, and check you see
the "GameShelf loaded 42 games" message. If you do, you are ready.

## The rules

- **No media queries needed.** The design is built so that Flexbox handles every screen
  size on its own — see "Narrow screens" in `design/DESIGN.md`. Media queries are two
  courses away and this project does not want one.
- **No libraries or frameworks.** No React, no jQuery, no Bootstrap, no Tailwind. Plain
  HTML, CSS and JavaScript.
- **No APIs, no `fetch`, no `async`/`await`.** If you find yourself googling a games API,
  stop — that is the next course. Your data is in `data/games.js` and it is enough.
- **Flexbox, not Grid** — even if you already know Grid. The layout in the mockup is built
  entirely with `flex-wrap`, and doing it that way is a deliberate constraint: Flexbox is
  what you were drilled on, and this is the project that makes it stick. There is a stretch
  goal at the bottom for rebuilding the grid with CSS Grid afterwards and comparing them.
- **Do not edit `data/games.js`.** Treat it as a database you do not control. Real ones
  usually are.
- **Do not redesign it.** Build what is in `design/`. Hitting a spec exactly is the skill
  being practised here.
- **Commit *and push* after every step below.** Not at the end — as you go. Your uncle is
  going to be watching the repo and the live site between calls, so if it is only on your
  laptop, nobody can help you with it.
- **No AI writing your code.** Same rule as the rest of your apprenticeship. Asking an AI to
  explain an error, or handing it code you already wrote and asking what is wrong with it, is
  fine and encouraged. Asking it for the answer to step 7 is not — step 7 *is* the point.

## The assignment

Do these in order. Each one works on its own, so you always have something you can look at,
and something worth pushing.

### 1. Get one card on the screen

Hard-code nothing. In `app.js`, take `GAMES[0]` and build a card element for it in
JavaScript, then put it on the page. Title, year, developer, rating.

Make it ugly. Make it work first.

### 2. Get all forty-two on the screen

Loop over `GAMES` and do the same thing for each one. You now have a very long single
column of ugly cards. That is correct.

### 3. Put it online — now, not at the end

Push what you have, then turn on **GitHub Pages** in the repository's Settings → Pages
(source: deploy from `main`, root folder). A minute later you have a real URL with your name
on it.

If Pages is not offered, your repo is Private — Settings → General → Danger Zone → Change
visibility → Public, and it will appear.

Do this *now*, while it is still ugly. Two reasons. Deploying is the part beginners leave
until last and then discover is broken, and you want to discover that on day one with four
files, not on day ten with four hundred lines. And from here on, **every push updates the
live site**, so anyone helping you can see exactly where you are without asking you to
explain it.

From this step onward: finish a step, commit it, push it. Every time.

**While you are in there, open your progress checklist.** Issues tab → New issue → pick
**Project progress** → Create. It arrives pre-filled with every step in this README. Pin it
(⋯ → Pin issue) so it sits at the top of the tab.

Tick the boxes as you go — GitHub saves a tick instantly, no commit needed — and drop the
Pages URL in a comment on it. That issue is the one place anyone can look to see where you
are, including you on a Tuesday when you have forgotten where you left off.

### 4. Make it a grid, and make the cards match the design

This is the CSS step, and it is the one people will actually notice.

**Read [`design/DESIGN.md`](design/DESIGN.md) properly before you start.** It specifies every
colour, size and spacing value, and [`design/tokens.css`](design/tokens.css) — already linked
from `index.html` — defines them all as CSS variables. You should not type a single hex code
in this project. Write `var(--space-4)`, not `16px`.

There are no image files. Every game has a `coverFrom` and `coverTo` colour, so the cover is
a CSS gradient you build in JavaScript.

When you think you are finished, open `design/mockup-desktop.png` next to your page and hunt
for differences. There will be more than you expect. Noticing them is the skill.

### 5. Add a search box

As the user types, only games whose title matches stay on screen.

Make it case-insensitive, and make it match anywhere in the title, not just the start —
typing `zelda` should find *The Legend of Zelda: Breath of the Wild*.

### 6. Add sorting

A `<select>` with at least: title A–Z, title Z–A, newest first, oldest first, highest rated,
and shortest first (that is `avgHours`).

**Read this bit twice, because it is the trap:** `.sort()` changes the array you call it
on. It does not hand you back a new one. If you sort `GAMES` directly, you have just
permanently scrambled your source data, and the bug that causes will not look like a
sorting bug at all. Find out how to sort a *copy*.

### 7. Add genre filters

Do not type the genre list out by hand. Build it from the data — loop over every game,
collect every genre, throw away the duplicates. There are a few ways to do that with what
you know. If a game with a brand new genre appeared in `data/games.js`, your filter list
should grow on its own without you touching a line of code.

A game can have more than one genre, so `genres` is an array. `.includes()` is your friend.

Multiple genres can be active at once. Decide whether that means "Action **and** RPG" or
"Action **or** RPG" — both are defensible, but pick one deliberately and be consistent.

### 8. Add platform filters

Same idea, using `platforms`. Build the list from the data again.

### 9. Make everything work together

Search, plus genre filters, plus platform filters, plus a sort order — all at the same time.

If this step feels like your code is falling apart, that is the actual lesson of this
project, and here is the shape of the answer:

> Keep the active search text, the selected genres, the selected platforms and the current
> sort in a few variables. Write **one** function that starts from `GAMES`, applies the
> filters, sorts the result, clears the grid, and rebuilds it. Every control does the same
> two things: update a variable, then call that one function.

The instinct to fight is hiding and un-hiding cards that are already on the page. It works
fine with 42 games and it is the wrong habit — it falls apart the moment sorting and
filtering have to combine.

### 10. Show the count, and handle nothing

A line that says `Showing 12 of 42 games`, updating live.

And when the filters match nothing at all, show the empty state from the design — a real
message with a way out, not a blank white void.

### 11. Check it on a phone

Grab the corner of your browser window and squash it down to phone width.

Here is the good news: **if you built step 4 faithfully, this should mostly already work,
and you are not expected to write a media query.** Those come up two courses from now. The
`flex: 1 1 260px` on the cards means the browser fits as many per row as will go — four,
then three, then two, then one — without you ever telling it how many columns to use. See
the "Narrow screens" section of `DESIGN.md`, and `design/mockup-narrow.png` for the target.

So this step is *finding what didn't come for free*. Usually it is a fixed `width` where a
`max-width` belonged, or something with a `min-width` bigger than the screen. Nothing should
ever scroll sideways.

Then open your live GitHub Pages URL on your actual phone, because that is the only test
that counts.

### 12. Finish it

Rewrite this README as your own: what it is, a screenshot, the live link, and a line about
what you learned. Put the live URL in the repository description too. Then strip out every
leftover `console.log` and every block of commented-out dead code.

## Requirements checklist

This list also lives in your **Project progress** issue, where the boxes are clickable —
tick them there rather than here. Before you call it done:

- [ ] All 42 games render from the array, with nothing hard-coded in the HTML
- [ ] It matches the mockup — spacing, colours and type, not just roughly the same shape
- [ ] Every colour and spacing value comes from `tokens.css`, no raw hex codes in your CSS
- [ ] Live search by title, case-insensitive, matching anywhere in the title
- [ ] At least six sort options, and sorting never mutates `GAMES`
- [ ] Genre filter, with the list built from the data
- [ ] Platform filter, with the list built from the data
- [ ] Search, both filters and sort all work simultaneously
- [ ] A live "showing X of Y" count
- [ ] The empty state, with a way to clear the filters
- [ ] Works at phone width, checked on a real phone, with no sideways scrolling
- [ ] Keyboard focus is visible everywhere you can tab to
- [ ] No libraries, no `fetch`, no Grid
- [ ] Deployed to GitHub Pages, with the URL in the repo description
- [ ] Pushed incrementally — a dozen or so meaningful commits, not one called "done"
- [ ] Your own README, with a screenshot and the live link
- [ ] No leftover `console.log` calls, no commented-out dead code

## Stretch goals

Only after the checklist is green. Most of these are real topics from the next course, so
expect to have to look things up.

- **Favourites.** A star on each card, and a "favourites only" toggle. Then make it survive
  a page refresh with `localStorage`.
- **A detail view.** Click a card, get a larger panel with the full blurb. Closable with
  the Escape key.
- **Rebuild the grid with CSS Grid** on a branch, keep the Flexbox version on `main`, and
  write a paragraph in your README on which one suited this layout better and why. That
  paragraph is worth more than the code.
- **A year range slider**, so you can ask for everything from 2015 to 2020.
- **Sort by two things at once** — rating, then title for ties.
- **Deep-link the filters** into the URL, so you can send someone a link to "co-op
  platformers, highest rated first".

## Hints, and the things that will actually bite you

- **Build the smallest thing that runs, then grow it.** One card before forty-two. One
  filter before four. If you sit down to write the whole thing at once you will spend the
  evening debugging four mistakes at the same time.
- **`.sort()` mutates. `.filter()` and `.map()` do not.** Know which is which before step 6.
- **`console.log` is not a last resort, it is the tool.** Log the array after filtering and
  before sorting. Look at what you actually have, not what you assume you have.
- **If `querySelector` returns `null`,** either you spelled the selector wrong or your
  script ran before the element existed.
- **Clear the grid before you rebuild it,** or every re-render will pile another 42 cards
  on top of the last lot.
- **A function that is longer than your screen wants to be two functions.** Remember the
  Clean Code lesson: `renderGames`, `createCard` and `getActiveFilters` are all better names
  than one enormous `doStuff`.
- **When you are stuck, read the error out loud.** It is almost always telling you exactly
  what is wrong — people just skip past it because it looks scary.
- **Push before you stop for the night**, even if it is half-finished. A broken commit
  someone can see beats perfect work nobody can.

Good luck. Take your time on step 4 and step 9; those are the two that will make this thing
worth showing off.
